知光搜索接口游标分页分析

后端技术调研 · 范围：SearchController / SearchServiceImpl · 生成于 2026-09-09

一、整体方案

  • 存储引擎：Elasticsearch（索引名 zhiguang_content_index），不是 MySQL LIKE。
  • 分页方式：ES 的 search_after，不是 from/size，也不是 scroll API。
  • 游标形态：5 字段 sort 数组 → 逗号拼接 → Base64URL 无填充编码，整体作为一个字符串塞进 query string 的 after 参数。
这是 ES 官方推荐的无状态分页方式。比 scroll 轻量（scroll 要在协调节点维护 context，1.5 分钟过期还得显式清理），比 from/size 不会越翻越慢。

二、5 字段复合排序（切片规则）

搜索结果按以下 5 个字段依次排序，content_id 作为最后一级 tie-breaker，保证同 score / 同时间时顺序完全确定，避免跳页或重复：

顺序字段方向作用
1score（_score，相关度）desc主排序：和关键词的匹配分
2publish_timedesc相关度相同时，更新的内容靠前
3like_countdesc进一步 tie-break：热度
4view_countdesc进一步 tie-break：曝光
5content_iddesc最终唯一排序键，杜绝同分重复

对应实现：SearchServiceImpl.java:54-59

sorts.add(SortOptions.of(s -> s.score(o -> o.order(SortOrder.Desc))));
sorts.add(SortOptions.of(s -> s.field(f -> f.field("publish_time").order(SortOrder.Desc))));
sorts.add(SortOptions.of(s -> s.field(f -> f.field("like_count").order(SortOrder.Desc))));
sorts.add(SortOptions.of(s -> s.field(f -> f.field("view_count").order(SortOrder.Desc))));
sorts.add(SortOptions.of(s -> s.field(f -> f.field("content_id").order(SortOrder.Desc))));

三、游标编码（服务端 → 客户端）

每次搜索后，服务端从命中的最后一条记录里取出它的 sort 数组，按固定顺序拼成字符串，再 Base64URL 编码：

SearchServiceImpl.java:153-154

List<String> parts = sv.stream().map(this::fieldValueToString).collect(Collectors.toList());
nextAfter = Base64.getUrlEncoder().withoutPadding()
                  .encodeToString(String.join(",", parts).getBytes());

Base64URL（而不是标准 Base64）的目的是：结果可以直接放在 URL query string 里，不用再处理 +///= 的转义。withoutPadding 让长度更可控。

真实样例（解码后）：

0.97654321,1725846400000,123,456,789
└─score─┘ └─publish_time─┘ └li└v└id┘

                              _   w
                              co  _
                              un  co
                              t    un
                                   t
                                   _i
                                   d

编码后传给前端：

after = "MC45NzY1NDMyMSwxNzI1ODQ2NDAwMDAwLDEyMyw0NTYsNzg5"

四、游标解码（客户端 → 服务端）

客户端下次请求把 after 原样回传，服务端按位置硬解析回 ES 的 FieldValue[]：

SearchServiceImpl.java:220-244

String decoded = new String(Base64.getUrlDecoder().decode(after));
String[] parts = decoded.split(",");
// i=0 → Double（score）
// i=1 → Long（publish_time）
// i=2..4 → Long（like_count / view_count / content_id）

解析出的 FieldValue 数组直接塞进下一次 ES 查询的 searchAfter 字段，ES 就能从"上一页最后一条之后"继续取。

六、设计取舍

  • 用 Base64URL 而不是 JSON：因为字段类型和顺序都是固定的，按位置拆最简单；URL safe 是为了让游标能直接挂在 URL 上。
  • 没抽 CursorUtil 工具类：编解码逻辑直接写在 SearchServiceImpl 里。可以理解为"专用，不通用"——目前搜索是唯一用 ES 的地方，没必要过早抽象。
  • 不暴露 sort 内容：前端只透传 after 字符串，不知道里面是什么。游标是 opaque token，这是对的。
  • 5 字段而非 2 字段：多 3 个 tie-breaker 看似冗余，但 ES 的 search_after 要求 sort 严格全局有序，差一个 tie-breaker 就可能出现"上一页最后一条同时也是下一页第一条"或跳页。
潜在风险：
1. 排序规则一旦改了（比如新增 comment_count），所有正在使用的 after 游标全部失效——需要兼容期或在解码失败时 fallback 到首页。
2. after 没设过期时间。理论上可以无限续翻。ES 这边没问题（无状态），但客户端如果缓存了旧的 after，可能在结果集已经大变的索引上产生乱序。当前未发现这类问题。
